2. STEP-BY-STEP STATE TRANSITION TABLE

Step 1:
- Current State: Five independent, raw shopping lists maintained separately in memory.
- Trigger / Real-Time Event: Mall entry and synchronization phase.
- Operation / Action: Group items by mall zone and aggregate overlapping items across lists (Diyas: 12 + 24 = 36; Wrapping paper: 5 + 10 = 15; Chocolates: 5 + 3 = 8; Dry fruits: 1 kg + 500 g).
- Updated State: Consolidated Master Procurement Matrix generated; redundant cross-shopping eliminated.

Step 2:
- Current State: Arjun's list contains "Wrist Watch - Titan, Quantity: 1".
- Trigger / Real-Time Event: Father calls and notifies that the watch was purchased online.
- Operation / Action: DELETE / CANCEL record where Friend == "Arjun" and Item == "Wrist Watch".
- Updated State: Arjun's list node removed and freed; inventory requirement adjusted.

Step 3:
- Current State: Priya's list contains 10 distinct festive clothing/accessory items.
- Trigger / Real-Time Event: Mother calls and requests to add a silk shawl.
- Operation / Action: INSERT / ADD record ("Silk Shawl", Kashmiri, Quantity: 1) into Priya's partition.
- Updated State: Priya's list size updated to 11 items; budget parameters re-verified.

Step 4:
- Current State: Kavin's list contains "Bluetooth Speaker - boAt, Quantity: 1".
- Trigger / Real-Time Event: Brother requests replacement with Wireless Earbuds within same budget.
- Operation / Action: UPDATE / REPLACE record: change ItemName to "Wireless Earbuds", confirm unit price <= Speaker budget.
- Updated State: Record modified in-place; budget integrity preserved without reallocating nodes.

Step 5:
- Current State: Meena's list contains "Decorative Flower Vase, Quantity: 1".
- Trigger / Real-Time Event: Message received requesting two additional flower vases for relatives.
- Operation / Action: UPDATE / INCREMENT quantity field: Quantity = Quantity + 2 (1 -> 3).
- Updated State: Meena's item count updated to 3; cost total recomputed.

Step 6:
- Current State: Sanjay's list contains "Smart LED TV - 43 inches (Samsung)".
- Trigger / Real-Time Event: In-store stock verification indicates selected Samsung model is out of stock.
- Operation / Action: SEARCH catalog for substitute with identical specifications and comparable price; UPDATE to LG 43-inch alternative.
- Updated State: Model reference updated to available stock; procurement process proceeds without stall.

Step 7:
- Current State: Master aggregated procurement list finalized with validated quantities.
- Trigger / Real-Time Event: Products identified across multiple aisles carrying BOGO and combo promotional offers.
- Operation / Action: Execute pricing evaluation: min(BOGO Price, Combo Price, Standard Price) for each SKU.
- Updated State: Optimal promotional pricing applied across all items; raw subtotal computed.

Step 8:
- Current State: Procurement complete; friends arrive at checkout with collected items.
- Trigger / Real-Time Event: Mall operates two checkout streams: Clothing Counters (FIFO) and Express Zone (Multi-Server).
- Operation / Action: Direct apparel items to Clothing Queue; distribute remaining items across Express Counters using greedy earliest-finish-time dispatching.
- Updated State: Parallel processing across registers minimizes makespan and customer queue delay.

Step 9:
- Current State: Unadjusted total bill computed across all registers.
- Trigger / Real-Time Event: Friends qualify for the shortest-time purchase criterion.
- Operation / Action: Verify completion of all original/updated requirements; deduct 30% Festival Bonanza discount.
- Updated State: Final payable bill produced; 30% coupon applied successfully.


3. ALGORITHM & PSEUDOCODE

3.1 Master Optimization Algorithm

ALGORITHM FestivalShoppingOptimizer:
    Input: Individual shopping lists L[1..5]
    Output: Consolidated bill, discount verification, minimum checkout time

    1. INITIALIZE MasterCatalog as HashTable
    2. INITIALIZE ClothingQueue as FIFOQueue
    3. INITIALIZE ExpressZone as MultiServerQueue(Counters = K)

    // Stage 1 & 2: Ingestion and Deduplication
    4. FOR each list in L[1..5] DO:
           FOR each item in list DO:
               IF MasterCatalog.CONTAINS(item.Name) THEN:
                   MasterCatalog[item.Name].Quantity += item.Quantity
                   MasterCatalog[item.Name].Subscribers.APPEND(item.Owner)
               ELSE:
                   MasterCatalog.INSERT(item.Name, item)
               END IF
           END FOR
       END FOR

    // Stage 3: Event-Driven Dynamic Updates (CRUD)
    5. PROCEDURE HandleDynamicEvent(Event e):
           SWITCH e.Type:
               CASE DELETE:
                   MasterCatalog.REMOVE(e.Friend, e.ItemName)
               CASE INSERT:
                   MasterCatalog.ADD(e.Friend, e.NewItem)
               CASE REPLACE:
                   MasterCatalog.UPDATE_FIELDS(e.Friend, e.OldItem, e.NewItem)
               CASE INCREMENT:
                   MasterCatalog[e.ItemName].Quantity += e.DeltaQty
           END SWITCH
       END PROCEDURE

    // Stage 4: Promotion Selection Engine
    6. SubTotal = 0.0
    7. FOR each item in MasterCatalog DO:
           OfferA = ComputeBOGO(item.Quantity, item.UnitPrice)
           OfferB = ComputeComboDiscount(item.Quantity, item.UnitPrice, item.Category)
           item.FinalPrice = MIN(OfferA, OfferB, item.Quantity * item.UnitPrice)
           SubTotal += item.FinalPrice
       END FOR

    // Stage 5: Load-Balanced Billing Simulation
    8. Separate MasterCatalog into:
           ClothingItemsList -> Dispatched to ClothingQueue
           GeneralItemsList  -> Dispatched to ExpressZone
    9. CheckoutDuration = MAX(SimulateFIFO(ClothingQueue), SimulateGreedyLoadBalance(ExpressZone))

    // Stage 6: Final Bonanza Deduction
    10. GrandTotal = SubTotal * 0.70  // 30% Bonanza Coupon applied
    11. RETURN GrandTotal, CheckoutDuration
END ALGORITHM


3.2 Express Zone Multi-Server Dispatching Logic

ALGORITHM SimulateGreedyLoadBalance(ExpressQueue, CounterCount):
    1. INITIALIZE CounterFinishTime[1..CounterCount] = {0}
    2. WHILE ExpressQueue IS NOT EMPTY DO:
           customer = ExpressQueue.DEQUEUE()
           serviceDuration = customer.ItemCount * UNIT_SCAN_TIME
           
           // Route customer to the counter that becomes free earliest
           minCounter = ARGMIN(CounterFinishTime)
           CounterFinishTime[minCounter] += serviceDuration
       END WHILE
    3. RETURN MAX(CounterFinishTime)
END ALGORITHM


4. DATA STRUCTURES USED ACROSS STAGES

Stage 1 & 2: List Intake & Duplicate Coordination
- Data Structure: Hash Table with Separate Chaining (Key: ItemName)
- Primary Operations: O(1) average insertion, lookup, and quantity accumulation.

Stage 3: Dynamic In-Flight Modifications (CRUD)
- Data Structure: Doubly Linked List for each individual friend context
- Primary Operations: O(1) node deletion (given pointer), O(1) front insertion.

Stage 4: Promotion & Pricing Evaluation
- Data Structure: Flat Array of Records / Contiguous Struct Buffer
- Primary Operations: Cache-friendly sequential iteration for formula evaluations.

Stage 5A: Clothing Counter Processing
- Data Structure: FIFO Linear Queue (Singly Linked List implementation)
- Primary Operations: Enqueue at tail upon arrival, dequeue from head upon servicing.

Stage 5B: Express Billing Zone Load Balancing
- Data Structure: Min-Priority Heap (or tracking array for small counter count K)
- Primary Operations: Extract-Min in O(log K) to identify the next available register.


5. JUSTIFICATION OF CHOSEN DATA STRUCTURES

Hash Table vs. Flat Array / Unsorted List (Aggregation Stage):
When multiple individuals purchase common items (e.g., Diyas, Wrapping Sheets, Chocolates), searching an unsorted array takes O(N) comparisons per item, leading to O(N * M) overall overhead. A Hash Table provides O(1) expected time for lookups and insertions, allowing instantaneous deduplication, aggregation of quantities, and departmental grouping.

Doubly Linked List vs. Fixed-Size Array (CRUD Update Stage):
Shopping requirements change dynamically in real time (cancellations, additions, substitutions). A fixed array requires O(N) data shifting on deletions and risks static buffer overflow on additions. A Doubly Linked List enables dynamic heap allocation, allowing O(1) node deletions and insertions once the target node is located, eliminating memory wastage and array reallocations.

Min-Heap Priority Queue vs. Independent Static Queues (Billing Stage):
The Express Billing Zone operates as a multi-server queue where arriving customers are routed to whichever register finishes first. Assigning customers to fixed static queues causes head-of-line blocking (e.g., a customer with 35 items blocks quick transactions behind them). Using a Min-Heap to track counter finish times allows greedy assignment to the earliest available server in O(log K) time, minimizing total makespan and ensuring qualification for the 30% Festival Shopping Bonanza discount.
